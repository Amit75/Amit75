# Aarulya Sovereign Security Foundation

## Purpose

This document defines the non-bypassable security architecture for Aarulya Store and every Aarulya-owned application. It is intentionally stricter than a normal app-store checklist. A release is denied unless source, build, signing, verification, distribution, update and incident-readiness evidence all agree on the exact artifact digest.

## Security model

- Zero trust for source, builders, storage, networks, operators and release metadata.
- No security claim is accepted as a plain boolean or self-declaration.
- Every security result must be represented by a signed, time-limited attestation bound to the APK SHA-256 digest.
- Build, review, signing and release approval duties must be separated.
- No single person, server, credential or key may publish a release alone.
- Failure is deny-by-default: missing, expired, unverifiable or inconsistent evidence blocks publication and download.

## Standards alignment target

- OWASP MASVS and MASTG for mobile storage, cryptography, authentication, networking, platform interaction, code, resilience and privacy.
- NIST Secure Software Development Framework for organization-wide secure development practices.
- SLSA Build Level 3 for hardened build provenance and SLSA Source controls for protected, reviewed source history.
- TUF-style root, targets, snapshot and timestamp role separation for update metadata.
- Signed attestations and an immutable transparency record for artifacts, provenance, SBOMs and security results.

These are target controls. Compliance must be demonstrated with evidence; naming a standard is not evidence.

## Root of trust

### Root keys

- Five independent root keys.
- Three-of-five threshold required for root changes.
- Root keys remain offline except during recorded signing ceremonies.
- Keys are held by separate custodians and stored in hardware-backed devices.
- Root metadata has defined expiry, rotation and compromise-recovery procedures.

### Online roles

- Targets metadata requires at least two independent signatures.
- Snapshot and timestamp keys are separate from targets and root keys.
- Online keys are hardware-backed, scoped to one role and rotated regularly.
- No application signing key is reused as a store-metadata key.

## Source assurance

- Protected branches and immutable audit history.
- Signed source revisions or equivalent verified source identity.
- At least two source approvals; critical products target SLSA Source Level 4 two-party review.
- Builder, reviewer and release approver identities are distinct.
- Change intent, threat-model impact and security impact are recorded for each release.
- Emergency changes remain reviewable and receive post-event independent review.

## Build assurance

- Hermetic, isolated and ephemeral builders.
- Pinned toolchains, dependencies and build inputs.
- No long-lived CI credentials; short-lived workload identity only.
- Build network access denied by default and allowlisted where unavoidable.
- Signed provenance generated by the trusted build platform.
- Minimum SLSA Build Level 3 target.
- Two independent builders reproduce the same artifact digest before release.
- Build logs, provenance and environment identities are retained as immutable evidence.

## Dependency and asset assurance

- Complete signed SBOM for application and native components.
- Lockfile and dependency allowlist verification.
- Malware, typosquatting, maintainer-change and abandoned-package review.
- Licence and asset-origin policy checks.
- No known critical vulnerability and no high vulnerability outside the defined remediation SLA.
- Every icon, screenshot, font, sound, model, template, book and film asset has ownership or licence evidence.

## Mobile application assurance

- Risk-based OWASP MASVS coverage with MASTG evidence.
- Secure storage and hardware-backed keys where supported.
- Strong cryptography through maintained platform libraries.
- Secure authentication, server-side authorization and session revocation.
- TLS-only networking and no user bypass for certificate failures.
- Safe Android intents, providers, deep links, WebViews and file handling.
- Release hardening, anti-tamper controls where justified and no debug/test credentials.
- Data minimization, permission minimization and explicit user consent.
- Child-directed applications receive a dedicated safety and privacy assessment.
- Finance, store, browser, cloud and security applications require independent penetration testing and red-team exercises.

## Signed evidence system

Required attestations include:

- source review
- SLSA build provenance
- independent reproducible build
- SBOM
- dependency scan
- secret scan
- static analysis
- dynamic analysis
- MASVS verification
- privacy review
- release approvals
- rollback readiness

Critical applications additionally require independent penetration-test, red-team, key-compromise recovery, disaster-recovery and break-glass attestations.

Every attestation must include:

- exact artifact SHA-256
- issuer identity and role
- signing key identity
- issue and expiry times
- result and evidence digest
- secure evidence location
- verified signature
- transparency-log inclusion proof

Expired, duplicated, mismatched or self-issued evidence is rejected.

## Update security

- Signed catalog and release manifests.
- Root, targets, snapshot and timestamp role separation.
- Protection against rollback, freeze, mix-and-match and fast-forward attacks.
- Metadata expiry enforced.
- Package ID, publisher, signing-key ID and signer certificate continuity.
- APK hash verified after download and before installation.
- Revocation lists, package kill switches and global emergency stop.
- Staged rollout with health gates and automatic rollback.

## Transparency and audit

- Artifact, provenance, SBOM, attestation and release events enter an append-only transparency log.
- Inclusion proofs are stored with the release.
- At least two independent witnesses verify log consistency.
- Public security summaries expose permissions, data use, security-review date and release provenance without exposing private secrets.

## Incident and recovery readiness

- Named incident commander and security contact.
- Tested key rotation, key compromise, release revocation and rollback procedures.
- Tested backup restore and disaster recovery.
- Security monitoring, tamper alerts and vulnerability response SLAs.
- Critical systems require a tested break-glass procedure with after-action review.

## Release decision

A release is eligible only when all of the following agree on the same APK digest:

1. source and review records
2. independent build outputs
3. signed provenance
4. SBOM and security scans
5. MASVS and privacy verification
6. signer and update metadata
7. release approvals
8. transparency-log record
9. rollback and incident-readiness evidence

Any mismatch or missing evidence produces a hard failure. There is no owner override that silently bypasses these gates.

## Current implementation boundary

The repository currently contains policy and validation foundations. It does not yet claim that offline root ceremonies, HSM-backed signing, hardened builders, cryptographic verification, independent rebuild infrastructure, transparency witnesses, penetration tests or production deployment are operational. Those controls must be implemented and tested before any APK is described as sovereign-secure or production-ready.
